# Medusa Feature

## Goal
Design the feature to match the Medusa v2 version actually used in the repository and the project's existing architecture.

## Stage 1: Discovery
- Check the `@medusajs/*` versions in the manifests and the lockfile.
- Find the related modules, workflows, subscribers, API routes, links, event handlers and configuration.
- Determine whether the feature belongs to an existing Medusa mechanism or needs its own module.
- When unsure, check the documentation for the version in use. Do not blindly rely on examples from another version.
- Do not run migrations, scripts, tests or builds without agreement.

## Stage 2: Design
Before implementing, describe:
- the data flow and responsibilities;
- the Medusa mechanisms used;
- changes to the API/admin/checkout, if applicable;
- the impact on the database and migrations;
- error handling, retries, idempotency and data consistency, if applicable;
- environment variables and required configuration;
- the tests and commands proposed to run.

Follow the architecture rules in `CLAUDE.md`: a thin API route → a workflow made of steps → a module, module links and Query instead of direct SQL, schema changes only through migrations generated by Medusa.

Prefer existing modules and patterns. Do not add dependencies or build your own infrastructure if the framework already provides a suitable mechanism.

Stop and ask for approval of the plan.

## Stage 3: Implementation
After approval:
- make only the approved changes;
- stay compatible with the version actually installed;
- do not change data or run migrations in a shared/production environment without separate approval;
- do not reveal secrets.

## Stage 4: Report
List the changed files, the Medusa mechanisms used, the configuration required for it to work, migrations, the approved checks and unresolved risks.
