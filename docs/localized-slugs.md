# Localized Slugs

Per-locale URL slugs for products, kept separate from Medusa's Translation
module (which handles `title`/`description`/`material`) and separate from
the core `product.handle` field.

## Why a separate module

Medusa's core `Product` model does **not** mark `handle` as `.translatable()`
(unlike `title`, `subtitle`, `description`, `material`), and the Translation
module's `updateTranslationSettings` rejects any attempt to register a field
that the underlying DML model didn't declare translatable. Localizing the
URL therefore can't go through the Translation module - it needed its own
module, linked to Product via a **Module Link**, so the two modules stay
isolated (`product.handle` is never touched or replaced).

## Architecture

```
Product (core)  <--Module Link-->  LocalizedSlug (this module)
                                         |
                                    (product_id, locale, slug)
```

- `src/modules/localized-slugs/models/localized-slug.ts` - the `LocalizedSlug`
  data model: `id`, `product_id`, `locale`, `slug` (+ standard
  `created_at`/`updated_at`/`deleted_at`).
- `src/modules/localized-slugs/service.ts` - thin `MedusaService` wrapper;
  no custom methods, just generated CRUD.
- `src/modules/localized-slugs/utils/slug.ts` - pure slug normalization/
  validation (`normalizeSlug`, `isValidSlug`, `assertValidSlug`), unit
  tested independently of the database.
- `src/links/localized-slug-product.ts` - the module link between
  `product.product` and `localized_slugs.localized_slug`.
- `src/workflows/localized-slugs/upsert-localized-slugs.ts` - the
  `upsertLocalizedSlugsWorkflow`, the only way slugs are written.

## Data model & constraints

| Field | Type |
|---|---|
| `id` | text, primary key |
| `product_id` | text |
| `locale` | text (BCP 47, e.g. `pl-PL`) |
| `slug` | text |

Enforced in the database (not just in application code):

- **Unique `(product_id, locale)`** - a product has at most one slug per
  locale.
- **Unique `(locale, slug)`** - a slug can't be reused by another product
  within the same locale. The same slug string *is* allowed across
  different locales (`pl-PL: shoes` and `en-US: shoes` can coexist).

Both are partial unique indexes (`WHERE deleted_at IS NULL`, generated by
`medusa db:generate`), so soft-deleting a row frees up its slug immediately
and a later `restore` doesn't collide with itself.

## Slug format

Canonical form: lowercase letters, digits and single hyphens
(`^[a-z0-9]+(-[a-z0-9]+)*$`), max 200 characters - e.g. `koszulka-meska`,
`t-shirt-basic`.

`assertValidSlug` trims and lowercases the input, then validates the
*result* against that pattern. Structurally invalid input (spaces, `/`,
`?`, `#`, doubled or leading/trailing hyphens, empty string) is **rejected**
rather than silently rewritten - `"koszulka--meska"` is an error, not
auto-collapsed to `"koszulka-meska"`. This keeps the normalization rule a
single regex instead of two divergent code paths (validate vs. repair).

## Locale

Locales are plain BCP 47 strings (`pl-PL`, `en-US`, ...), normalized with
Medusa's own `normalizeLocale` (`@medusajs/framework/utils`) - the same
function the Translation module and the `applyLocale` request middleware
use. There's no separate locale registry or config for this module; it
relies entirely on the store's existing supported locales.

## Upsert semantics

`PUT /admin/products/:id/localized-slugs` takes the **full desired state**
for a product: any locale present in the request is created or updated,
any locale the product currently has but that's *missing* from the request
is removed. There's no "empty string deletes" sentinel - omission is the
only way to delete a locale's slug.

```
before:  pl-PL -> stary-slug
request: [{ locale: "pl-PL", slug: "nowy-slug" }, { locale: "en-US", slug: "new-en" }]
after:   pl-PL -> nowy-slug (updated in place, not duplicated)
         en-US -> new-en (created)
```

```
before:  pl-PL -> x, en-US -> y, de-DE -> z
request: [{ locale: "pl-PL", slug: "x" }]
after:   pl-PL -> x
         en-US, de-DE removed
```

## Workflow & compensation

`upsertLocalizedSlugsWorkflow` steps, in order:

1. `validateProductExistsStep` - 404s if the product doesn't exist.
2. `getExistingLocalizedSlugsStep` - reads the product's current slugs.
3. normalize + validate every incoming `{locale, slug}` (400 on the first
   invalid one, and on a duplicate locale within the same request).
4. diff against the existing rows -> `toCreate` / `toUpdate` /
   `toDeleteIds`.
5. `checkSlugConflictsStep` - proactively rejects (409) any `(locale, slug)`
   already owned by a *different* product, before any write happens. This
   is the friendly check; the database's unique index is the last line of
   defense (see below).
6. `createLocalizedSlugsStep`, `updateLocalizedSlugsStep`,
   `deleteLocalizedSlugsStep` - the actual writes.

Each write step has a real compensation function:

- create -> compensates by **soft-deleting** the rows it just created.
- update -> compensates by **restoring the previous slug value** (captured
  from step 2, *before* the update ran) - not by deleting the row.
- delete -> compensates by **restoring** (`restoreLocalizedSlugs`) the rows
  it soft-deleted.

If a later step fails (e.g. a genuine race lands after the proactive check
passed), the workflow engine unwinds by calling these compensations in
reverse, so a product is never left half-updated.

`createLocalizedSlugsStepInvoke/Compensate`,
`updateLocalizedSlugsStepInvoke/Compensate` and
`deleteLocalizedSlugsStepInvoke/Compensate` are exported as plain functions
(not just inline `createStep` closures) specifically so they can be
exercised directly in tests against a real database, independent of the
workflow orchestration engine - see
`src/modules/localized-slugs/__tests__/service.spec.ts`.

### Races and the database as last line of defense

`checkSlugConflictsStep` catches the common case, but two concurrent
requests could both pass it before either writes. The database's unique
index is what actually prevents the bad state; when it fires, Medusa's
default DB-error mapper turns it into a generic `INVALID_DATA` ("already
exists") error. The create/update steps re-map that specific case to a
`CONFLICT` error, so a real race still surfaces as `409`, not `400` or a
raw Postgres error.

## API

### Admin

```
GET  /admin/products/:id/localized-slugs
PUT  /admin/products/:id/localized-slugs
```

`GET` returns the current state:

```json
{ "localized_slugs": [{ "locale": "pl-PL", "slug": "koszulka-meska" }] }
```

`PUT` body is the full desired state (validated by a Zod schema for shape;
slug format is validated by the workflow):

```json
[
  { "locale": "pl-PL", "slug": "koszulka-meska" },
  { "locale": "en-US", "slug": "mens-t-shirt" }
]
```

Errors: `400` invalid slug/locale or malformed body, `404` product not
found, `409` slug already used by another product in that locale.

### Store

```
GET /store/products/by-slug/:slug
```

Locale comes from Medusa's existing locale resolution (`?locale=pl-PL` or
the `x-medusa-locale` header - the same `applyLocale` middleware every
other store route uses). Requires a valid `x-publishable-api-key`, like
every other store route.

```http
GET /store/products/by-slug/koszulka-meska?locale=pl-PL
x-publishable-api-key: pk_...
```

```json
{ "product_id": "prod_123", "locale": "pl-PL", "slug": "koszulka-meska" }
```

`400` if no locale is provided, `404` if there's no slug for that exact
`(locale, slug)` pair (a slug registered under `pl-PL` is *not* found when
queried under `en-US`).

**Deliberately minimal response.** This endpoint only resolves
`(locale, slug) -> product_id` - it does not return product title, images,
variants or pricing. The Localized Slugs module's job is the URL mapping
only (see "Why a separate module" above); fetching the actual product is
already solved by `GET /store/products/:id` (or `?id[]=`), which already
returns exactly the fields/relations the storefront needs without this
module having to re-implement or guess at product serialization.

## Using it from Nuxt

```ts
// e.g. /pl/produkty/koszulka-meska -> locale "pl-PL", slug "koszulka-meska"
const { product_id } = await $fetch(
  `${backendUrl}/store/products/by-slug/${slug}`,
  {
    query: { locale },
    headers: { "x-publishable-api-key": publishableKey },
  }
)

const { product } = await $fetch(`${backendUrl}/store/products/${product_id}`, {
  headers: { "x-publishable-api-key": publishableKey },
})
```

## Migrations

Generated with the standard Medusa flow:

```bash
npx medusa db:generate localized_slugs   # generates the migration from the model
npx medusa db:migrate                     # applies it + syncs the module link
```

No data backfill migration exists for existing products - the module is
additive and empty by default. Populate slugs product-by-product through
the admin API (or a manually-run one-off script) instead of an automatic
bulk-generation migration, since there's no rule in the codebase for
deriving a "correct" slug from existing data (see the project's own
`add-polish-translations.ts` for the pattern used for adjacent
translation-seeding, which the same "run a script when you're ready"
approach follows).

## Testing

Three layers, matching the project's existing `TEST_TYPE` convention
(`apps/backend/jest.config.js`):

- **Unit** (`pnpm test:unit`) - `slug.unit.spec.ts`: normalization/validation
  only, no database.
- **Module integration** (`pnpm test:integration:modules`) -
  `service.spec.ts`: real Postgres, the module in isolation. Covers create,
  multi-locale, update-in-place, soft-delete, both unique-constraint
  violations, same-slug-different-locale, locale+slug lookup, and the three
  step compensation functions called directly (see above).
- **HTTP integration** (`pnpm test:integration:http`) -
  `integration-tests/http/localized-slugs.spec.ts`: boots the full app and
  exercises the actual admin/store routes, including the 400/404/409 status
  codes and the update/delete-by-omission semantics end to end.

### One-time local setup this project didn't have yet

Two pieces of test infrastructure were missing from this repo entirely
(unrelated to this feature - nothing here previously had a test) and were
added as part of this work:

- `apps/backend/integration-tests/setup.js` - referenced by
  `jest.config.js` but didn't exist, so *no* test could run before this.
- `apps/backend/.env.test` - `DB_HOST`/`DB_PORT`/`DB_USERNAME`/`DB_PASSWORD`
  for a **local** Postgres instance. `@medusajs/test-utils` ignores the
  app's own `DATABASE_URL` entirely for tests and always builds its own
  connection from these `DB_*` variables (defaulting to `localhost`), so
  module/HTTP integration tests never touch the real (remote) database
  configured in `.env`.

One more one-time step, specific to this machine: `moduleIntegrationTestRunner`'s
auto-provisioning (`MikroORM`'s `ensureDatabase()`) can't create its own
throwaway database on this local Postgres install - the very first
connection attempt is made *against the not-yet-existing database itself*,
which Postgres refuses outright. `medusaIntegrationTestRunner` (the HTTP
runner) doesn't have this problem, since it provisions the database
through `pg-god` first. Work around it once with:

```bash
psql -h localhost -U postgres -c 'CREATE DATABASE "medusa-localized_slugs-integration-1";'
```

The database persists across runs (only its schema is reset between
tests), so this is a one-time step, not a per-run one.

## Architectural decisions worth flagging

- **Module Link, not `product.metadata`.** Keeps slugs queryable/unique at
  the database level and keeps the Product model untouched.
- **Workflow, not a single service method**, for the write path - this is
  what makes real per-step compensation possible (a plain "upsert everything
  in one call" can't roll back step N without also being step N+1).
- **Reject invalid slugs, don't auto-repair them.** `"Koszulka--Meska"` is
  a 400, not a silent rewrite to `"koszulka-meska"` - the caller sees
  exactly what's wrong instead of Medusa guessing their intent.
- **Store endpoint returns only `product_id`,** not a full nested product -
  deliberately narrower than the reference implementation this module took
  inspiration from, to avoid duplicating `GET /store/products/:id`'s
  responsibility and to avoid overfetching relations the storefront may not
  need for every lookup.
